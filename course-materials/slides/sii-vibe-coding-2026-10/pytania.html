Co włożyć do AGENTS.md, CLAUDE.md i copilot-instructions.md?

Fakty: Codex odczytuje AGENTS.md, Claude Code używa CLAUDE.md i importów @plik.md, a Copilot ma repozytoryjne .github/copilot-instructions.md. Zakres obsługi zależy od narzędzia.

Zalecenie: zacznij od krótkiej mapy projektu, rzeczywistych poleceń uruchomienia i testów, granic architektury, zakazów oraz definicji ukończenia. W nowym dla agenta repo poproś najpierw o odczyt manifestów, CI i przykładowego modułu, bez zmian. Zatwierdź ustalenia, dopiero potem utwórz instrukcje. Nie wpisuj nieistniejących poleceń.

Przykład: "Przed dodaniem walidatora znajdź istniejący. Po zmianie pokaż diff, wykonane testy i niewykonane kontrole". Wspólne reguły trzymaj w jednym źródle; dla Claude można użyć CLAUDE.md z importem @AGENTS.md. Dla Copilota sprawdź, które pliki stosuje wybrany interfejs.

Na zajęciach: dzień 1, moduł 4: Workflow.

Sprawdzono: 2026-10-17. Źródła: Claude Code: pamięć i reguły, Codex: AGENTS.md, Copilot: mapa instrukcji, skills i hooków.

Jeden duży plik czy instrukcje według domen i zadań?

Fakty: Claude Code obsługuje .claude/rules/*.md z polem paths, a Copilot instrukcje ścieżkowe .github/instructions/*.instructions.md z applyTo. Codex buduje instrukcje ze ścieżki od katalogu projektu do katalogu startowego; nie zakładaj, że wszystkie zagnieżdżone pliki wczyta przy starcie.

Zalecenie: w głównym pliku umieść reguły całego repo. Reguły domeny dopisz blisko kodu, a procedurę konkretnego rodzaju pracy zapisz jako skill. Nie powielaj tej samej treści w wielu plikach.

Przykład: główna reguła zakazuje zmiany publicznego API bez decyzji; instrukcja katalogu płatności wymaga testu ponowienia żądania. Przed zmianą poproś agenta o wskazanie aktywnych instrukcji i sprawdź to małą próbą.

Na zajęciach: dzień 1, moduł 4: Workflow.

Sprawdzono: 2026-10-17. Źródła: Claude Code: pamięć i reguły, Codex: AGENTS.md, VS Code: zakres instrukcji.

Jak egzekwować reguły i uporządkować wymagania jakościowe?

Fakty: instrukcje językowe mogą zostać pominięte. Hooki uruchamiają kod na zdarzeniu; konfiguracja i odpowiedź blokująca zależą od narzędzia. W Claude Code i Codex zdarzenie nazywa się PreToolUse, w Copilocie preToolUse.

Zalecenie: każdą regułę opisz przez warunek i dowód. Wymagania niefunkcjonalne powiąż z testem lub pomiarem; architekturę z ADR i zależnościami; commity z małym zakresem; samosprawdzenie z konkretnymi poleceniami i wynikiem. Twarde zakazy wesprzyj uprawnieniami, hookiem i CI.

Próba: w przykładach hooków porównaj blokowany odczyt fikcyjnego .env z dozwolonym .env.example. Obejrzyj skrypt i scal konfigurację, zamiast zastępować dotychczasową. W Codex przejrzyj i zatwierdź hooki przez /hooks. Wzorce w przykładzie nie obejmują każdej składni powłoki i nie zastępują izolacji ani skanera sekretów.

Na zajęciach: dzień 1, moduł 4; bezpieczeństwo: moduł 7: Workflow.

Sprawdzono: 2026-10-17. Źródła: Claude Code: schemat hooków, Codex: hooki, Copilot: hooki, Kod i testy demonstracyjne.

Jak dzielić zadania i opisać kryteria jakości kodu?

Zalecenie: jedno zadanie powinno dać jeden wynik, który da się osobno odebrać. Brief zawiera cel użytkownika, zakres plików, ograniczenia, kryteria akceptacji i sposób sprawdzenia. Zależności realizuj po kolei; prace niezależne można rozdzielić.

Przykład: "Dodaj walidację numeru zgłoszenia. Pusty numer pokazuje komunikat, poprawny tworzy jedno zgłoszenie, ponowne kliknięcie nie dubluje zapisu. Użyj istniejącego walidatora. Nie zmieniaj API ani zależności. Pokaż testy tych zachowań i diff". Jakość oznacza zgodność z zachowaniem i konwencjami projektu, a nie samą kompilację.

Jaka kolejność pracy i ile człowieka w pętli?

Zalecenie: kontekst i specyfikacja, decyzje architektoniczne, plan, mała implementacja z testami, review, akceptacja i scalenie. Testy planujesz przy wymaganiach; przy zmianie zachowania warto najpierw uzyskać test, który wykazuje brak funkcji lub błąd.

Człowiek zatwierdza wymagania, ryzykowne decyzje, dostęp do danych i wynik przed scaleniem. Agent może sam wykonać odwracalne kroki w zaakceptowanym zakresie. Nie potrzebujesz zgody po każdym odczycie pliku.

Przykład: zatwierdź regułę zwrotu towaru i przypadki brzegowe. Pozwól agentowi zaimplementować jeden przypadek, a potem porównaj działanie z kryteriami, zamiast akceptować samo "gotowe".

Na zajęciach: dzień 1, moduły 2-3; dzień 2, moduł 9: Implementacja.

Czy po każdym cyklu uruchamiać wszystkie testy?

Zalecenie: dobieraj testy do wpływu i ryzyka zmiany. W krótkiej pętli uruchom test zmienionego zachowania, testy bezpośrednich zależności oraz szybkie kontrole statyczne. Przy zmianie wspólnego kontraktu, schematu danych lub konfiguracji rozszerz zakres. Przed scaleniem muszą przejść wymagane kontrole CI; nie pomijaj ich dlatego, że agent wykonał test jednostkowy.

Przykład: zmiana walidacji formularza wymaga testów walidatora i wysyłania formularza; zmiana wspólnego modelu zgłoszenia także testów API i zapisu. Poproś: "Wskaż zależne moduły, wybierz testy i uzasadnij pominięte". Sprawdź, czy test umie wykryć celowo wprowadzony błąd, a nie tylko powtarza implementację.

Jak pracować kilkoma agentami w jednym repozytorium?

Fakt: Git worktree daje dodatkowy katalog roboczy z własnym indeksem i checkoutem, przy współdzielonym repozytorium Git. Nie izoluje sam z siebie procesów, sieci ani sekretów.

Zalecenie: zacznij od jednego agenta. Przy równoległej implementacji osobne branche i worktree ułatwiają rozdzielenie zmian. Wspólny katalog dopuszczaj tylko przy rozłącznych plikach i jednym koordynatorze operacji Git. Nie pozwalaj agentom równocześnie przełączać brancha ani aktualizować lockfile.

Przykład: agent A zmienia walidator, agent B tylko dokumentację; wspólny kontrakt zatwierdzacie wcześniej. Koordynator sprawdza oba diffy, scala i testuje całość. Dla worktree zaplanuj osobne porty, zależności i usunięcie katalogu po zakończeniu; koszt zależy od projektu i menedżera pakietów.

Jak wprowadzić agenta do dużego istniejącego projektu?

Zalecenie: zacznij w trybie odczytu od inwentarza modułów, manifestów, punktów wejścia, CI i sposobu uruchomienia. Zapisz krótką mapę repo i instrukcje. Potem prześledź jeden rzeczywisty przepływ wraz z testami i konfiguracją, zanim zlecisz zmianę.

Przykład: "Pokaż drogę od formularza do zapisu zgłoszenia. Każdą zależność uzasadnij plikiem i symbolem; zaznacz luki. Nie edytuj".

Wniosek z próby opisanej w notatce: repo map daje szkic struktury, graf pomaga szukać wywołań, ale relacje wywnioskowane i brak odwołań wymagają sprawdzenia w źródłach. Nie uznawaj klasy za martwą tylko dlatego, że indeks jej nie połączył. Wyniki małej próby nie gwarantują kompletności dla firmowego monorepo.

Na zajęciach: dzień 1, moduły 2 i 4: Workflow.

Sprawdzono: 2026-10-17. Źródła: Notatka: legacy-repository-analysis, Notatka: code-graph-tools-vs-repo-maps-2026-10-14.

Jak ograniczać kontekst i kiedy wybrać droższy model?

Fakty: okno kontekstowe obejmuje instrukcje, historię, wyniki narzędzi i odpowiedź. Jego rozmiar oraz reguły naliczania zależą od modelu. Abonament narzędzia i opłaty API to odrębne rozliczenia. Jak oceniać kod agenta i używać AI do review kodu człowieka?

Fakt: Copilot code review może proponować uwagi do zmian w PR, lecz nie zastępuje przeglądu człowieka. Kod napisany przez człowieka i agenta oceniaj według tych samych kryteriów.

Zalecenie: daj recenzentowi diff, wymaganie, istniejące wzorce i wyniki testów. Poproś o usterki z warunkiem wystąpienia, skutkiem i lokalizacją, nie o kosmetykę. Sprawdź bezpieczeństwo, zgodność zachowania, przypadki brzegowe, zależności i niepotrzebne abstrakcje.

Przykład: przed dodaniem klienta API agent ma wyszukać istniejący klient i opisać różnicę. Recenzent dostaje polecenie: "Znajdź błąd i pokaż odtwarzający go test. Nie zmieniaj plików". Drugi model daje dodatkową perspektywę, ale jego zgodność z pierwszym nie jest dowodem poprawności.

Na zajęciach: dzień 2, moduł 6: Review i CI.

Sprawdzono: 2026-10-17. Źródła: GitHub: code review, Przykład agenta do review.

Jakie praktyki wdrażać w wielu zespołach?

Zalecenie: wspólne minimum to klasy danych dopuszczonych do agenta, zasady zgód, małe PR, instrukcje repo, testy w CI i człowiek odpowiedzialny za scalenie. Domeny dopisują własne reguły zamiast kopiować wielką centralną instrukcję.

Przykład pilota: wybierz powtarzalny rodzaj zadania w kilku repozytoriach. Porównaj czas od wymagania do zaakceptowanego PR, liczbę poprawek i regresji oraz koszt. Zapisz przypadki, w których AI nie pomogła. Zespół utrzymuje instrukcje razem z kodem i usuwa reguły, które się zdezaktualizowały.

Administrator może ograniczać funkcje narzędzi polityką organizacji; dostępność funkcji w dokumentacji nie oznacza zgody na użycie firmowych danych.

Jak współpracują AI, agent, GitHub i IDE, także Eclipse z Javą?

Fakty: model generuje odpowiedzi; agent dodaje odczyt plików, edycję i polecenia. IDE służy do pracy z kodem, a GitHub hostuje repozytorium i przeglądy. Agent lokalny może pracować przed wysłaniem zmian do GitHuba.

  • Eclipse: GitHub Copilot ma rozszerzenie z czatem i trybem Agent. Otwórz Copilot Chat, wybierz Agent, wskaż zadanie i przejrzyj zmiany oraz polecenia.
  • Claude Code: oficjalna integracja JetBrains współpracuje z CLI; zewnętrzny terminal można połączyć przez /ide. Dokumentacja nie potwierdza analogicznej oficjalnej wtyczki do Eclipse.
  • Codex: oficjalna dokumentacja wskazuje rozszerzenie dla VS Code i zgodnych edytorów oraz integrację JetBrains przez AI Chat. Nie potwierdza oficjalnego rozszerzenia Eclipse.
  • Terminal obok IDE: Claude Code i Codex CLI mogą pracować w katalogu projektu Java otwartym w Eclipse. IDE i agent muszą widzieć te same pliki; zapisz zmiany w edytorze i sprawdzaj diff.

Start: zbuduj mały formularz zgłoszenia z jednym scenariuszem, testem i commitem. Osoba nieprogramująca prosi o wyjaśnienie każdego zmienionego pliku i sama sprawdza zachowanie. GitHub dołącz po lokalnej weryfikacji.

Na zajęciach: dzień 1, moduł 1: Narzędzia.

Jak używać agenta w bashu i ograniczać AI, żeby rozumieć wynik?

Fakty: Claude Code i Codex to także narzędzia terminalowe; uruchomienie claude lub codex rozpoczyna interaktywną pracę. Dostęp do powłoki zależy od uprawnień sesji.

Zalecenie: zostaw zwykłe polecenia powłoce, a AI użyj tam, gdzie potrzebujesz analizy albo zmiany. Zacznij od git status i git diff; agent nie musi pośredniczyć w każdym poleceniu.

Przykład promptu: "Wyjaśnij ten błąd i zaproponuj jedno polecenie diagnostyczne. Nie zmieniaj plików. Opisz jego działanie i wynik, którego oczekujesz". Następnie wykonaj polecenie świadomie. Po zmianie poproś o wyjaśnienie diffu i sprawdź, czy umiesz opisać przepływ własnymi słowami.

Na zajęciach: dzień 1, moduły 1 i 3: Narzędzia.

Sprawdzono: 2026-10-17. Źródła: Claude Code: CLI, Codex: CLI.

Jak przejść od makiety do większego systemu web i mobile?

Zalecenie: makieta opisuje wygląd i część interakcji, ale nie ustala uprawnień, modelu danych, integracji ani zachowania przy błędach. Najpierw spisz role, przepływy i kryteria akceptacji. Dopiero potem wybierz architekturę w ADR i podziel rozwój na małe pionowe fragmenty.

Przykład: pierwszy fragment obejmuje utworzenie zgłoszenia, walidację, zapis i odczyt statusu. Web i mobile korzystają z uzgodnionego kontraktu API. Każdy fragment ma test kontraktu, test błędnego wejścia i demonstrację zachowania. Osobno ustal logowanie, prywatność, tryb offline, powiadomienia i wdrażanie.

Nie zlecaj "zbuduj cały system z obrazka". Po pierwszym fragmencie oceń kod i dopiero rozpisz następny. Warsztat ćwiczy ten proces; kompletna aplikacja mobilna wymaga osobnego zakresu.

Na zajęciach: dzień 1, moduł 2; dzień 2, moduł 9: Implementacja.

Jak cofnąć pracę agenta?

Fakty: Copilot CLI udostępnia /undo i alias /rewind: cofnięcie rozmowy albo rozmowy i śledzonych plików. Pliki później zmienione ręcznie są pomijane; cofanie nie działa w sesji zdalnej ani podczas trwającej pracy. VS Code oferuje przywracanie checkpointów w przeglądzie zmian.

Zalecenie: najpierw obejrzyj podgląd, potem sprawdź git status i git diff. Wycofanie rozmowy nie odwraca wysłanej wiadomości ani operacji na zewnętrznym systemie. Mały, sprawdzony commit daje niezależny punkt powrotu. Nie cofaj cudzej niezapisanej pracy.

Na zajęciach: dzień 1, moduł 3: Workflow.

Sprawdzono: 2026-10-17. Źródła: Copilot: cofanie i ograniczenia, VS Code: checkpointy.

Co odróżnia zgody na narzędzia od samodzielnego kontynuowania pracy?

Fakty: w VS Code poziom zgód określa, które wywołania wymagają potwierdzenia; Autopilot dotyczy autonomii sesji. Dostępność poziomów i ich ustawień zależy od wybranego harnessu oraz polityki organizacji. Włączenie narzędzia nie oznacza automatycznej zgody na każdą akcję.

Zalecenie: zacznij od ograniczonego zapisu do projektu i kontroli operacji sieciowych. Pozwalaj na powtarzalne, odwracalne kroki w uzgodnionym zakresie. Publikację, migrację danych i działania na produkcji oceniaj osobno.

Przykład: uruchomienie lokalnego testu może być dozwolone, a wysłanie pliku na obcy serwer wymaga zatrzymania i wyjaśnienia. Przejrzyj uprawnienia w swojej wersji narzędzia, zanim zwiększysz autonomię.

Dlaczego skill lub instrukcja nie działa w moim IDE?

Fakt: obsługa instrukcji, skills i hooków różni się między interfejsami Copilota. Dokumentacja wymienia projektowe katalogi skills, w tym .agents/skills/<nazwa>/SKILL.md, ale nie każda funkcja działa na każdej powierzchni.

Zalecenie: sprawdź wersję rozszerzenia, aktualną macierz wsparcia i wybranego agenta. Potwierdź, czy plik został wykryty i zastosowany. Nie kopiuj go w wiele miejsc bez diagnozy. Skill zapisany w katalogu materiałów kursu jest przykładem do adaptacji, nie automatyczną konfiguracją ćwiczonej aplikacji.

Próba: użyj prostej, łatwej do rozpoznania reguły w nieszkodliwym zadaniu. Jeśli agent jej nie zastosuje, sprawdź zakres i logi ładowania przed wydłużaniem promptu.

Na zajęciach: dzień 1, moduł 4: Workflow.

Gdzie trafia historia sesji i czy mogę ją synchronizować?

Fakty: w VS Code synchronizację historii kontroluje chat.sessionSync.enabled; można wykluczać repozytoria przez chat.sessionSync.excludeRepositories. Polityka organizacji może wymusić wyłączenie. Zsynchronizowane sesje są powiązane z osobistym kontem GitHub i domyślnie prywatne.

Zalecenie: przed pracą na kodzie firmy sprawdź ustawienia i politykę. Przy przekazaniu zadania zapisz decyzje, zakres zmian i wyniki testów w repozytorium lub uzgodnionym narzędziu. Sama historia rozmowy nie zastępuje dokumentacji projektu. Przykład: kolejna sesja zaczyna od planu i aktualnego diffu, zamiast zgadywać stan z poprzedniej rozmowy.

Na zajęciach: dzień 2, moduł 7: Bezpieczeństwo.

Czy Copilot indeksuje repozytorium i czy muszę dodawać #codebase?

Fakty: Copilot w VS Code udostępnia wyszukiwanie semantyczne #codebase. Agent może użyć go samodzielnie. Edytor automatycznie utrzymuje indeks; źródło indeksu zależy od repozytorium i środowiska. Polecenie Build Codebase semantic index pozwala zażądać budowy lub przebudowy.

Zalecenie: pytaj o konkretny przepływ i żądaj lokalizacji w źródłach. Przykład: "Gdzie sprawdzamy prawo do zwrotu? Pokaż funkcję, wywołania i testy". Wynik wyszukiwania pomaga znaleźć kod, ale nie dowodzi kompletności zależności ani aktualności wszystkich założeń.

Co oznacza Agent Host i gdzie wykonuje się kod?

Fakt: VS Code rozróżnia lokalnego agenta rozszerzenia i Agent Host, osobny proces obsługujący agentów. Nazwa "Local" nie dowodzi, że model działa na Twoim komputerze. Miejsce wykonywania poleceń i dostawca modelu to dwa osobne ustalenia.

Zalecenie: przed zapisem poproś o katalog roboczy, system i gałąź. W pracy zdalnej potwierdź, czy terminal, IDE i agent używają tego samego środowiska. Przykład: plik zmieniony w Linuksie w WSL musi być tym samym plikiem, który oglądasz w IDE, a nie drugą kopią projektu.

Na zajęciach: dzień 1, moduł 1: Narzędzia.

Czy własny klucz API albo lokalny agent oznacza pracę offline?

Fakt: własny klucz API określa rozliczenie i dostawcę; nie dowodzi lokalnego przetwarzania. Lokalnie uruchomiony agent może wysyłać kontekst do modelu w chmurze. Obsługa własnych modeli i protokołów zależy od narzędzia.

Zalecenie: rozdziel zgodę organizacji, lokalizację danych, dostawcę i rozliczenie. Dla pracy offline potrzebujesz także lokalnego modelu i zależności, które nie wymagają sieci. Przed użyciem sprawdź konfigurację na syntetycznym projekcie, zamiast wnioskować z etykiety "local" lub "BYOK".

Jak wykorzystać agenta w CI/CD?

Fakty: Claude Code ma tryb nieinteraktywny claude -p, a Codex codex exec. Można uruchamiać je ze skryptu, przy odpowiednim dostępie i uwierzytelnieniu. Przykłady kursu obejmują automatyczne review; konfigurację trzeba dopasować do hostingu i polityki organizacji.

Zalecenie: zacznij od raportu do PR bez prawa zapisu i publikacji. Testy, lint i skaner sekretów pozostają niezależnymi kontrolami. Agent może analizować diff i wskazać ryzyka, człowiek ocenia uwagi i decyduje o scaleniu. Kod z PR traktuj jako niezaufany; nie uruchamiaj go z sekretami produkcyjnymi.
