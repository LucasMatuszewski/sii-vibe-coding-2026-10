## Research method and limits

Queried current Context7 documentation for known library IDs `/vercel/ai` and `/vercel/next.js`, then inspected actual public GitHub repository metadata, pinned trees and raw files. The official [AI SDK template index](https://ai-sdk.dev/resources/templates) links a full chatbot and the Next.js example; its marketing labels alone were not used to infer dependencies. Read manifests, environment examples where present, route/provider implementations, layouts and license text.

Four concrete starter candidates were compared below. Additional official OpenRouter provider source was checked solely for compatibility and whether it contained a Next.js starter. No key was read, no environment provisioned, no model invoked and no inference charge incurred. Public source was fetched into temporary research files under `/tmp/`; no clone, archive extraction, generator, package install or application edit occurred. Commit pins are research snapshots, not a claim that these are the newest releases at future implementation time.

### Official OpenRouter availability and compatibility

The bounded search did not identify a lean, current official OpenRouter Next.js starter suitable for this signed-case application. That is a search result, not a claim that none exists. OpenRouter's live tool-calling demo is a separate product example; its page's public source link pointed to Vercel's chatbot lineage, so it was not treated as proof of an independent maintained starter. The official [OpenRouter provider repository](https://github.com/OpenRouterTeam/ai-sdk-provider/tree/1b22b05352cb0f9243a6c3fdd326038dd3705544) tree at the inspected pin had no `examples/` Next.js application; it is a provider package, not a scaffold. The [official integration guide](https://openrouter.ai/docs/community/frameworks) supports using the provider with AI SDK.

The provider's [current official README](https://github.com/OpenRouterTeam/ai-sdk-provider#setup-for-ai-sdk-v7) states that its SDK 7 line supports `ai ^7.0.0`, requires Node >=22 and is ESM-only. Retain the already accepted Node 24 / SDK 7 / OpenRouter provider 3 baseline from ADR-001; do not copy an SDK 5 provider bridge or substitute another model/key. Exact installed peers and a successful type/build check remain P01 evidence, not a compatibility claim established by browsing.

## Why this starter rather than the current empty Next template

The current official [Next create-next-app template](https://nextjs.org/docs/app/api-reference/cli/create-next-app) remains the lowest-drift framework shell: it avoids upgrading this donor's Next 15 configuration. It does not supply this donor's already configured shadcn primitives, `cn` utility, Tailwind 4 UI setup and AI-app project organization. Selecting it would return to the empty-scaffold approach the user asked us to reconsider.

The donor's **SDK 5 → 7 migration would be significant if its chat route/component were retained**: request bodies, stream helpers, generic history trust, model selection and composer behavior do not meet ADR-002/003. This plan therefore excludes that behavior instead of trying to preserve/migrate it. Backend route development is already required by the product and remains in P08/P10/P12/P14. Reusing only the small framework/UI foundation bounds the remaining upgrade work to package/configuration alignment and source relocation, while preserving a concrete ready starter provenance. The supplied primitives are ordinary React components with local dependencies; they still require strict typing, build and accessible usage validation under the new target versions.

This is a judgment about fit, not a measured claim that adapting the donor is faster than all alternatives. If P01 discovers incompatibility beyond these named files, stop and report the concrete issue rather than silently growing a wholesale migration. The coordinator can then reconsider the current empty Next template with the user; there is one selected baseline today, not an automatic unapproved fallback.

## SDK and provider behavior belongs to later packages

The donor chat route trusts a client `messages` array/model ID and uses an old result response helper. The accepted application sends only signed context plus one stable text turn to `/api/chat`, streams UI Message protocol and commits through typed `data-commit` plus successful finish. Backend must implement these contracts from its own tests, not preserve the generic demo route and patch its provider name.

Current Context7 SDK documentation shows the SDK 7 stateless boundary: convert model messages with the current async contract, transform `result.stream` through `toUIMessageStream`, then return `createUIMessageStreamResponse`; see [official migration source](https://github.com/vercel/ai/blob/main/content/docs/08-migration-guides/23-migration-guide-7-0.mdx). Current Next documentation confirms removal of `next lint` and fully async request APIs; see [Next 16 upgrade guide](https://nextjs.org/docs/app/guides/upgrading/version-16). These are execution references, not evidence that copied code already compiles.

P05 obtains fresh safe real captures before any endpoint/provider response-shaped mock is created or refreshed. P08/P10/P12/P14 implement OpenRouter behavior and signed contracts through Red → Green → refactor. Unit dependency mocks are permitted only from those real capture shapes; integration mocks only the external LLM; E2E mocks nothing. No business/live API call is required or permitted merely to prove the P01 static baseline builds. Later real calls, retries, manual QA/E2E/evaluation and captures all count toward the **single USD 5 total OpenRouter validation cap across all roles**; coordinator tracks the aggregate budget before execution.
