## Shared contracts to deliver in P03

The following spellings are a **proposed implementation contract** for review under P03. Accepted ADR concepts and endpoint field names remain authoritative. Freeze exact enum wire spellings, nullability and SDK-compatible message/stream envelopes in that package before FE, fixtures or routes depend on them.

| Contract | Concrete fields/validation |
|---|---|
| `CaseForm` | `caseType` (return/complaint discriminant), `category` (the exact ten AC-03 options), trimmed `model` (2–100 Unicode code points), `purchaseDate` (ISO date, 2000-01-01 through signed submission date), `reason` (return optional ≤2000; complaint trimmed 10–2000). No user-supplied today/model override/policy path. |
| `ImageAnalysis` common | `caseType`, `imageUsable`, nullable `unusableReason` (blurry/too-dark/no-device/cropped/other), `deviceVisible`, `detectedDeviceType`, `categoryMatch` (matches/does-not-match/uncertain), `modelConsistency` (consistent/inconsistent/cannot-determine), `visibleSurfaces[]`, `findings[]`, `confidence` (high/medium/low). Each finding has `type`, `location`, `severity` from ADR-002. |
| Return analysis | Common fields plus `condition` (as-new/minor-handling/visible-use/damaged), `signsOfUse[]`, `resellability` (yes/no/uncertain), `packagingVisible`, `sealVisible`, `sealIntact` (yes/no/unknown). Invisible seal cannot be claimed intact. |
| Complaint analysis | Common fields plus `describedDefectVisible` (yes/no/partially), `likelyCause` (manufacturing/mechanical/liquid/tampering/normal-wear/not-determinable), `supportingVisibleEvidence[]`. No device implies unusable; invisible causes remain unknown. |
| `Decision` | `outcome` (accepted/rejected/needs-information), nonempty `policyReferences[]`, `justification`, ordered `nextSteps[]`, `missingInformation[]`, positive `revision` (initially 1). All rule IDs must belong to selected policy. |
| Decision card | Decision fields plus canonical Polish `label`, revision heading when applicable and exact server-owned `disclaimer`. Required next steps are validated typed data, not a streamed model status. |
| `UserFact` | `kind`, schema-validated `value`, exact `supportingQuotation` from pending text, `origin: user-asserted`, `turnId`. A fact does not overwrite image observations. |
| `TurnPlan` | `replyKind` (explanation/updated-decision/off-topic-refusal/unsupported-action), `candidateFacts[]`, optional `candidateDecision`, `preservedEvidenceReferences[]`, `allowedNextSteps[]`; accepted/authoritative plan produced only after rule validation. |
| `CanonicalMessage` | Stable `id`, `role` user/assistant, complete `text`, optional server-owned `decisionRevision`. No partial/reasoning/tool/system messages in canonical history. |
| `SignedCaseContext` | `schemaVersion`, `stage` analyzed/chat, internal `nonce`, immutable `form`/`analysis`, `submissionDate`, selected `policyHash`, signed server `processingDeadline` for initial creation. Chat adds current `decision`, `facts[]`, complete `messages[]`. JOSE fixed issuer/audience/algorithm are verified outside the payload schema. |
| Analyze request/result | Multipart `caseType`, `category`, `model`, `purchaseDate`, `reason`, one `photo`, `attemptId`, `remainingMs`; success `{analysis, signedContext, attemptId}`. Unknown control fields rejected. |
| Decide request/result | `{signedContext, attemptId, remainingMs}`; success `{decision, firstMessage, signedContext}`. `firstMessage` is a complete assistant UIMessage with canonical text and server-owned `data-decision`. |
| Chat request | `{signedContext, message: {id, text}}`; one new text-only user turn of 1–2000 code points, rejecting whitespace-only, files/tools/system/developer/reasoning/assistant parts and unsigned replacement state. |
| Final commit event | `data-commit` payload with `schemaVersion`, next `signedContext`, complete canonical assistant message and optional revised decision. Associate with pending stable message ID using the frozen SDK event contract. Successful protocol finish **and** valid final commit are both necessary for client adoption. |
| `ErrorEnvelope` | Stable machine `code`, safe Polish `message`, optional `fieldErrors`, `attemptId` where applicable, `retryable`. Freeze code/status mapping and retry meaning; no stack/prompt/token leakage. |

Keep UI labels exactly as PRD AC-18, and disclaimer byte-for-byte as AC-28. Semantic unknowns must not be coerced to false/absent. Enforce limits before inference: 10,000,000-byte photo inclusive; normalized longest side ≤2048; context string ≤1 MiB; chat body ≤2 MiB; assistant reply ≤12,000 Unicode code points. Multipart total size includes a separately documented overhead allowance so a valid 10 MB image is accepted. Do not silently trim history to satisfy these bounds.
